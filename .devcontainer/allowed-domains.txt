#
# Die Extensions selbst kommen damit NICHT durch. Der VS Code Server laedt sie
# von einer Subdomain je Herausgeber, <publisher>.gallerycdn.vsassets.io
# (Akamai), und das erst beim Verbinden -- also NACH der Firewall, auf die
# "waitFor" ausdruecklich wartet. Am 2026-10-05 im Log gesehen: ETIMEDOUT auf
# z. B. anthropic.gallerycdn.vsassets.io. Eine dig-basierte Allowlist kann
# keine Wildcards; alle diese Namen landen aber auf demselben Akamai-Pool.
#
# Bewusst nicht dauerhaft freigegeben (das oeffnete den ganzen Pool, ueber den
# auch fremde Akamai-Kunden erreichbar sind). Abhilfe ohne Freigabe: in den
# Benutzereinstellungen von VS Code AUF DEM HOST
#   "remote.downloadExtensionsLocally": true
# setzen, dann laedt VS Code die Extensions auf dem Host und spielt sie in den
# Container. Sonst die Adressen fuer eine Installation befristet ins ipset
# legen, sie laufen nach 15 Minuten von selbst ab.
# In einer Root-Shell vom Host aus (docker exec -it -u root claude-<projekt> bash):
#   for ip in $(dig +short A anthropic.gallerycdn.vsassets.io | grep -E '^[0-9.]+$'); do
#     ipset add allowed-domains "$ip" timeout 900 -exist; done
# Danach die Installation in VS Code neu anstossen.
